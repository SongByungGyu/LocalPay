# 01. 서비스 기획서

## 1. 프로젝트 개요

### 1.1 서비스명

- 가칭: **LocalPay Map**
- 한글 가칭 후보: 동네페이맵 / 우리동네상품권 / 페이동네
- MVP 개발 단계에서는 브랜딩을 고정하지 않는다.

### 1.2 문제 정의

온누리상품권과 지역화폐는 할인/지원 혜택이 있지만 사용자는 다음 문제를 겪는다.

- 주변 어디에서 사용할 수 있는지 찾기 어렵다.
- 공식 가맹점 목록은 지도 탐색 경험이 충분하지 않은 경우가 있다.
- 같은 가맹점이라도 온누리/지역화폐 중 어떤 수단이 가능한지 한눈에 보기 어렵다.
- “이 가게에서 무엇을 파는지” 정보가 부족하다.
- 데이터 갱신 시점과 실제 현장 결제 가능 여부가 다를 수 있다.
- 상품권 종류/지역별 할인정책을 여러 서비스에서 각각 확인해야 한다.

### 1.3 해결 방법

지도에 사용처를 통합하고, 다음 정보를 하나의 가맹점 상세 화면으로 제공한다.

- 지원 결제수단
- 현재 위치로부터 거리
- 업종/카테고리
- 취급 상품/대표 상품
- 주소/전화/영업정보
- 데이터 출처와 최근 확인 시점
- 사용자 자체 후기
- 실제 상품권 결제 성공/실패 인증
- 지역화폐 할인율/구매한도 등 정책정보

## 2. 핵심 가치 제안

### 사용자에게

> “지금 내 주변에서 이 상품권을 쓸 수 있는 곳을 10초 안에 찾는다.”

### 서비스 차별점

단순 가맹점 목록이 아니라 다음을 합친다.

1. **지도 탐색**
2. **결제수단 필터**
3. **상품/메뉴 검색**
4. **실사용 후기**
5. **최신성 표시**
6. **지역 정책 정보**

---

## 3. 목표 사용자

### Persona A — 일상 사용 사용자

- 지역화폐/온누리상품권을 가지고 있다.
- 점심, 장보기, 약국, 카페 등 일상 소비에 사용하고 싶다.
- “가까운 곳”, “지금 쓸 수 있는 곳”이 중요하다.

### Persona B — 전통시장/동네상권 이용 사용자

- 특정 시장 또는 동네를 방문한다.
- 어떤 가게에서 무엇을 살 수 있는지 미리 확인하고 싶다.
- 방문 전 상품권 사용 가능 여부를 확인하고 싶다.

### Persona C — 후기 기여 사용자

- 실제 결제 성공/실패 경험을 공유한다.
- 공공데이터의 최신성 부족을 사용자 정보로 보완한다.

### Phase 2 Persona D — 가맹점주

- 자기 가게의 영업시간, 사진, 상품, 메뉴를 직접 관리하고 싶다.
- MVP에서는 제외하되 데이터 모델 확장을 고려한다.

---

## 4. 서비스 목표

### MVP 목표

- 지도에서 사용처를 빠르게 찾는다.
- 결제수단과 카테고리로 즉시 필터링한다.
- 가맹점 상세에서 “무엇을 파는지”와 “어떤 상품권이 되는지”를 확인한다.
- 후기/결제인증 UI를 통해 서비스 차별 가능성을 검증한다.
- 실제 공공데이터 연결 전에도 더미 데이터로 전체 사용 흐름을 완성한다.

### 성공 기준 예시

MVP 내부 테스트 기준:

- 앱 실행 후 3탭 이내 가맹점 상세 도달
- 결제수단 필터 반응 즉시
- 지도 이동 후 새로운 영역 가맹점 재조회 흐름 명확
- 검색 결과에서 지도/리스트 전환 없이도 매장 확인 가능
- 즐겨찾기 저장/해제 유지
- Offline/데이터 없음/위치 권한 거절 UI 존재

## 5. 핵심 사용자 시나리오

### 시나리오 1 — 주변 온누리 음식점 찾기

1. 앱 실행
2. 위치 권한 승인
3. 홈 지도 표시
4. 결제수단 `온누리` 선택
5. 카테고리 `음식점` 선택
6. 지도 핀 또는 하단 카드 선택
7. 상세에서 온누리 지원 형태와 후기 확인
8. 길찾기 또는 전화

### 시나리오 2 — 상품으로 검색

1. 검색창에 `삼겹살` 입력
2. 상품/가맹점 통합 검색
3. `삼겹살` 취급 등록 매장 우선 표시
4. 온누리/지역화폐 필터 조합
5. 거리순/추천순 확인
6. 상세 진입

### 시나리오 3 — 약국 찾기

1. 홈에서 `약국` 카테고리 선택
2. 현재 지도 영역 내 상품권 사용 가능 약국 표시
3. 가까운 가맹점 선택
4. 전화/길찾기

### 시나리오 4 — 결제 경험 공유

1. 상세 → 후기 작성
2. 실제 결제 여부 선택
3. 사용수단 선택
4. 구입 품목/후기 입력
5. 등록
6. 상세에 최근 결제 확인 정보 반영

MVP에서는 서버 업로드 대신 로컬 더미 저장으로 시작 가능하다.

## 7. MVP / Phase 2 / Phase 3

- Dummy + 실제 SDK 적용 가능한 구조
- 지도 탐색
- 검색/필터
- 상세
- 후기 더미
- 즐겨찾기
- MY
- 잔액 Placeholder

### Phase 2

- 운영사 제휴 기반 잔액 조회

- 알림
- 쿠폰/이벤트/시장 행사
- 운영자 CMS

## 8. MVP에서 의도적으로 하지 않는 것

- 실제 상품권 결제 기능
- 충전/구매/환불
- 사용자의 금융정보 임의 수집
- 비공개 또는 비제휴 잔액 조회
- 외부 서비스 리뷰 크롤링
- 사업자 데이터 무단 복제

---

## 9. 서비스 정책 초안

### 가맹점 정보 신뢰도

각 정보에 출처를 가진다.

- `PUBLIC_ONNURI`
- `PUBLIC_LOCAL_CURRENCY`
- `KAKAO_PLACE`
- `MERCHANT_OWNER`
- `USER_VERIFIED`

사용자 화면에서는 필요 시 다음 형태로 표시한다.

- 공공데이터 기준
- 최근 사용자 결제 확인: 2일 전
- 가게에서 직접 수정: 2026-08-10

### 리뷰 정책

- 일반 후기 + 상품권 결제 인증을 구분한다.
- 실제 결제 여부는 사용자의 신고/경험 정보이며 공식 보증으로 표현하지 않는다.
- 욕설/개인정보/허위정보 신고 기능을 Phase 2에 포함한다.
